# Статическая типизация BSL (v8-code-style)

Стандарт: [code_typification.md](https://github.com/1C-Company/v8-code-style/blob/master/docs/checks/code_typification.md), [стандарт 1С: описание процедур и функций](https://its.1c.ru/db/v8std#content:453:hdoc).

## Новые модули

В **новых** `.bsl` файлах (в т.ч. `_POS5000`) первой строкой:

```bsl
// @strict-types
```

## Существующие модули без `// @strict-types`

Не включай `@strict-types` в старых модулях без явной просьбы. Вместо этого — **типизирующие документирующие комментарии** для экспортных и новых/изменённых методов:

```bsl
// Назначение метода.
//
// Параметры:
//  Имя - Тип - Описание
//
// Возвращаемое значение:
//  Тип - Описание
```

Для структур — поля с `*`. Для коллекций — `Массив из См. ...`, `ТаблицаЗначений`.

## Конструкция «см.»

Повторяющиеся или громоздкие описания типов **не дублируй** — ссылайся на **другой** уже описанный тип:

- параметр объекта формы: `см. Документ.ЗаказКлиента.Форма.ФормаДокумента.Объект`
- тип из другого метода: `Параметр - см. ИмяМодуля.ИмяФункции` — **без** повторения типа (`Структура`, `Булево` и т.д.), он берётся из возврата/описания в `см.`
- поле структуры как у другого метода: `см. ИмяФункции.ИмяПараметра`
- в коде — только если EDT не выводит тип: `Переменная = ДругойМодуль.Функция(); // см. ДругойМодуль.Функция`

**Не добавляй** `см.` на строке вызова функции на саму эту функцию — тип берётся из её документирующего комментария автоматически. Не ссылайся из тела метода на его собственный комментарий.

**Проверяй ссылки `см.` по метаданным:** путь вида `Документ.X.Форма.Y` должен существовать в конфигурации. Ориентируйся на предупреждения EDT (неразрешённая ссылка в документирующем комментарии). У `РасходныйКассовыйОрдер` форма — `ФормаДокумента`, не `ФормаДокументаРМК`.

## Минимум для изменённого кода

При правке BSL добавляй/обновляй типы в комментариях для **новых и изменённых** сигнатур. Не рефактори комментарии нетронутых методов.
